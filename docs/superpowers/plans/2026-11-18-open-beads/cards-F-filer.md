## Cluster F: Filer (file manager)

Owners today. `FileManagerWindow` (`src/Bevel.FileManager/FileManagerWindow.axaml.cs`, 1485 lines) is the view adapter: it owns the tree, the tab sessions, `LoadDirectory` (:831, streams 32-item chunks), `ReloadDifferential` (:1414, watcher/F5 keyed reconcile) and all menu wiring. `FileManagerController` owns navigation history, selection, clipboard and mutations (no Avalonia). `ItemView` (`Components/ItemView.axaml.cs`) is the list engine: an `ObservableCollection<ItemViewModel>` bound to an `ItemList : ItemsControl` inside an outer `ScrollViewer`; its own rect-based selection/marquee/keyboard model; code-built `FuncDataTemplate`s per `ViewMode`. Details uses Avalonia's `VirtualizingStackPanel` (:209) and does virtualize; Large/Small/List/Thumbnails use `VirtualizingWrapPanel`, which despite the name derives from `Panel` and measures every child (`VirtualizingWrapPanel.cs:19,62`). The VFS (`Bevel.Core/Vfs`: `VfsRoot`, `IVfsProvider`, `LocalFsProvider`, `ComputerProvider`, `TrashProvider`) is Avalonia-free. Icons are code-drawn vector glyphs (`Bevel.UI/Glyphs.cs`); the PAL already has `IIconProvider` (pooled through `PooledIconProvider`/`MmfBgraPool`) and `IThumbnailProvider`, registered in every role, but Filer uses neither.

Target design. (1) One list engine for every view mode: a uniform-cell `VirtualizingWrapPanel : VirtualizingPanel` with viewport realization, recycling and a one-page buffer, fed by a `SortedItemList` that merges whole sorted batches in O(n+m) with one collection event per flush; all geometry (hit, marquee, scroll-to-index) comes from one cell-metrics table, not from realized containers. (2) Enumeration off the UI thread is bevel-so27's job (other cluster); these cards consume its batches and do not duplicate it. (3) Icons stay vector-first: type icons are theme-token glyphs, native bitmaps appear only for per-file identity (`.app`) and content thumbnails, loaded off-thread by the shared `IconLoader`/`PreviewLoader` moved into `Bevel.UI`, requested only by realized rows. (4) Per-folder view state and Favorites are capped `string[]` keys in the settings blob, so the core stays the single writer and every Filer process converges through the existing snapshot push.

Open-core split (bevel-l4fg): every card keeps new UI inside `Bevel.FileManager` and new shared code in open projects (`Bevel.UI`, `Bevel.Core`, PAL), so none adds a new App-to-Filer link. Two things to know: bevel-ioxx adds two constructor parameters to `Bevel.App/FileManagerWindowFactory.cs` (one of the seven coupling files, same seam shape), and bevel-ze3o / bevel-4pgk add Filer-specific keys to the open `BevelSettings` (three already exist there).

**One design, four cards.** The bugs share a cause: view geometry is written down in five places that disagree (`ApplyViewMode` :214-234, the panel, `ColsPerRow` :944, `PageStep` :957, `ScrollToIndex` :964), and the name label is built without a width it can trim to. The set fixes that once:

- `WrapLayout` (new, pure, no Avalonia controls) is the only place that knows where item *i* is. The panel arranges from it, keyboard navigation moves by it, scroll-into-view reads it. It is the type bevel-rzz planned; these cards create it and bevel-rzz extends it.
- `ItemView.CellSize(ViewMode)` is the only place cell sizes are written.
- `NameLabel` (new, a `TextBlock` subclass) is the only name label. It always ends a cut-off name with an ellipsis, knows whether it is cut off, and shows the full name in a tooltip when it is.

**Rule for every headless test in this set.** After `window.Show()`, call `Dispatcher.UIThread.RunJobs()` **before** adding items. `ItemView` applies its view mode in `OnLoaded` (:182-186). If items arrive first, the first layout pass uses the default `StackPanel` and plain 15 px text rows, and Avalonia then leaves `ItemList` arranged at that stale height until the next resize (a control that its parent re-measures with a new constraint is not re-arranged when its arrange rectangle is unchanged). **Measured:** 5 items in Large Icons left `ItemList` 75 px tall where its desired height was 60. The real app loads items after `Loaded`, so this does not happen there; bevel-w912 makes the panel immune to it anyway and has one test that sets items first on purpose.

### bevel-w912 — Filer List view: columns are centred when they do not fill the width; should be left-aligned
- **Meta:** P2 · bug · size S · AGENT
- **State today:** Confirmed, and wider than the bead says. `VirtualizingWrapPanel.ArrangeOverride` returns `Extent()` (`VirtualizingWrapPanel.cs:86`), which is narrower than the slot whenever the items do not fill it. Avalonia's `Layoutable.ArrangeCore` centres a `Stretch`-aligned control whose `ArrangeOverride` returns less than its slot. **Measured** in an 830 px viewport with 5 items: List panel at x=325 (325 px of empty pane on its left); Large Icons at x=15; Small Icons and Thumbnails at x=55. Two more effects of the same line: (a) under RTL the panel mirrors with `final.Width` (:82) and is *then* centred, so the first List item lands at x=975, outside the 830 px viewport: a short RTL List view shows nothing; (b) when the slot is taller than the content (see the test rule above) icons shift down by half the difference (measured y=8). `ItemWidth`, `ItemHeight` and `Orientation` are registered without `AffectsMeasure` (:21-31), so changing one on a live panel does not re-lay it out; bevel-3fgd needs that.
- **Depends on:** none.
- **Files:** `src/Bevel.FileManager/Components/WrapLayout.cs` (new); `src/Bevel.FileManager/Components/VirtualizingWrapPanel.cs`; `tests/Bevel.FileManager.Tests/WrapLayoutTests.cs` (new); `tests/Bevel.FileManager.Tests/VirtualizingWrapPanelTests.cs`; `tests/Bevel.FileManager.Tests/ItemViewLayoutTests.cs` (new)
- **Decision:**
  - `WrapLayout`: `internal readonly record struct WrapLayout(int Count, int PerLine, int Lines, double ItemWidth, double ItemHeight, bool Horizontal)`. `Horizontal` = items flow left to right and wrap down (icon views); otherwise top to bottom, wrapping into columns (List).
    - `static WrapLayout Compute(int count, double lineSpan, double itemWidth, double itemHeight, bool horizontal)`: `PerLine = lineSpan is infinite or NaN ? max(1, count) : max(1, (int)(lineSpan / (horizontal ? itemWidth : itemHeight)))`; `Lines = (int)Math.Ceiling((double)count / PerLine)`. `count == 0` gives `PerLine` as computed and `Lines = 0`. This is the arithmetic at `VirtualizingWrapPanel.cs:54-59`, moved unchanged, including the infinite-span guard.
    - `Size Extent` = `Horizontal ? (PerLine * ItemWidth, Lines * ItemHeight) : (Lines * ItemWidth, PerLine * ItemHeight)`.
    - `Rect RectFor(int index, double finalWidth, bool rtl)`: line = `index / PerLine`, pos = `index % PerLine`; x = `Horizontal ? pos * ItemWidth : line * ItemWidth`; y = `Horizontal ? line * ItemHeight : pos * ItemHeight`; when `rtl`, x = `finalWidth - ItemWidth - x`.
  - `VirtualizingWrapPanel`: replace `_perLine`/`_lines` with `public WrapLayout Layout { get; private set; }`, set in `MeasureOverride` (which still returns `Layout.Extent`, so scrolling is unchanged). `ArrangeOverride` arranges child *i* at `Layout.RectFor(i, final.Width, rtl)` and returns `new Size(Math.Max(final.Width, e.Width), Math.Max(final.Height, e.Height))` where `e = Layout.Extent`. Returning the slot is what stops the centring; the `Max` keeps the result valid if a parent ever arranges it smaller than it measured.
  - Add `static VirtualizingWrapPanel() => AffectsMeasure<VirtualizingWrapPanel>(ItemWidthProperty, ItemHeightProperty, OrientationProperty);`.
  - Do **not** set `HorizontalAlignment.Left` on the panel instead: the panel would then be only as wide as its columns, and RTL mirroring needs the full slot width to start at the right edge.
- **Test first:** `VirtualizingWrapPanelTests.Columns_narrower_than_the_slot_start_at_the_left_edge` (new, `[AvaloniaFact]`): 5 `Border` children, 180x18, `Orientation.Vertical`; host the panel in `new Decorator { Child = p }`, `host.Measure(new Size(800, 40))`, `host.Arrange(new Rect(0, 0, 800, 40))`.
