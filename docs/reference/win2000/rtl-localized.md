# RTL & Localized (Hebrew/Arabic) — Win2000 reference notes

## Overview

Windows 2000 was the first NT-family release to ship a true bidirectional (BiDi) mirroring layer for Arabic- and Hebrew-enabled editions, exposed to apps via the `WS_EX_LAYOUTRTL` extended window style and `SetLayout(hdc, LAYOUT_RTL)` at the GDI device-context level. Under RTL, the whole window is conceptually rendered as if reflected in a vertical mirror placed at its center: text becomes right-aligned/right-to-left, the title-bar icon and Close/Maximize/Minimize buttons swap to the top-left, menu bars and toolbars read right-to-left, the Start button and taskbar move to the right edge of the screen, and directional glyphs (arrows, resize grips) flip horizontally. Non-directional imagery — logos, trademarks, checkmarks, up/down indicators — is explicitly excluded from mirroring. Because true Win2000-desktop-chrome screenshots of Arabic/Hebrew builds are scarce in public, non-Cloudflare-gated galleries, this note leans on a mix of a real Arabic Windows XP Explorer photo, Arabic-XP MessageBox photos, and a rendered (non-photographic) WinForms RTL mirroring illustration, plus the underlying Microsoft mirroring API documentation that describes exactly what the OS-level `WS_EX_LAYOUTRTL` transform touches.

## Key visual facts

- RTL layout is opt-in per window via the extended style `WS_EX_LAYOUTRTL` passed to `CreateWindowEx`; child windows inherit their parent's layout by default. Dialogs, message boxes, and unattached DCs (metafile/printer) do **not** inherit layout and must set it explicitly. — https://learn.microsoft.com/en-us/previous-versions/aa913269(v=msdn.10)
- To mirror a message box specifically, code must pass the `MB_RTLREADING` flag to `MessageBox`; to lay out a dialog template RTL, use `WS_EX_LAYOUTRTL` in `DLGTEMPLATEEX`, and for property sheets every tab needs the style individually. — https://learn.microsoft.com/en-us/previous-versions/aa913269(v=msdn.10)
- Under RTL, "the origin is positioned at the right edge of the window or device, and the number representing the horizontal coordinate increases as you move left" — i.e. x=0 is the right edge, not the left. — https://learn.microsoft.com/en-us/previous-versions/aa913269(v=msdn.10)
- On Arabic Windows XP Explorer (photo evidence, XP not Win2000 — see Images table): the title bar's Close/Maximize/Minimize button cluster sits at the **top-left** corner of the window (mirrored from the LTR top-right position), the title-bar icon is at the top-right, the menu bar reads right-to-left (File/Edit/View/Favorites/Tools become rightmost-to-leftmost), and the "Go" toolbar button that normally sits at the right end of the address bar in LTR appears at the left end. — https://flylib.com/books/en/3.147.1.90/1/ (Figure 7.5, "Windows Explorer on Arabic Windows XP")
- "In the desktop, notice that the Start menu is on the right and that the taskbar extends from right to left. Also notice the direction of all the arrows. Not only have the controls moved, but the images indicating directions have changed." — https://flylib.com/books/en/3.147.1.90/1/
- Zoomed pixel inspection of the rendered mirrored-vs-unmirrored WinForms sample (Images table) shows the **entire button order reverses**, not just repositions: LTR title-bar buttons read (left→right) Minimize, Restore, Close; the mirrored version reads (left→right) Close, Minimize, Restore — a true left-right flip of the whole cluster, matching a literal mirror reflection rather than a simple "move the cluster to the other side" relocation. — https://flylib.com/books/en/3.147.1.90/1/ (Figures 7.6–7.8), local zoom crop, see Images table
- Same sample: OK/Cancel button order flips — unmirrored reads OK, Cancel (left→right); mirrored reads Cancel, OK (left→right), so OK ends up on the right/near side, consistent with "near/far" mirroring rather than semantic re-ordering. — https://flylib.com/books/en/3.147.1.90/1/ (Figures 7.6–7.8)
- MessageBox comparison on Arabic Windows XP: "The Close button has moved from the right to the left, the OK and Cancel buttons have been transposed, and... the text is right-aligned instead of left-aligned." — https://flylib.com/books/en/3.147.1.90/1/ (Figure 7.9–7.10 captions)
- General Microsoft globalization guidance: "control handles and pull-down buttons should be mirrored on right-to-left documents. If a scroll bar is required, it appears on the left side of the control." — https://learn.microsoft.com/en-us/globalization/fonts-layout/mirroring
- Not everything mirrors: "common icons such as the fast-forward and rewind icons in media players use the same orientation in both LTR and RTL layouts" and separately, "Images that include a logo, textual trademark, or flag should not be reversed," "images that indicate an up or down direction should not be reversed," and "a check mark (a tick)... should not be reversed." — https://learn.microsoft.com/en-us/globalization/fonts-layout/mirroring and https://flylib.com/books/en/3.147.1.90/1/
- Direction-sensitive bitmaps (e.g. window resize-grip glyphs) must be explicitly re-flipped by the app/shell or they render wrong: "a Southeast-oriented resize bar will appear in the Southwest corner" if the bitmap itself isn't flipped along with the mirrored coordinate system. — https://www.chromium.org/developers/design-documents/ui-mirroring-infrastructure/
- Mixed-direction ("BiDi") text handling: the Arabic Explorer address bar keeps the LTR path string (`C:\Documents and Settings`) rendered left-to-right as an embedded run inside the overall RTL-flowing UI chrome, rather than reversing the path segments themselves — consistent with standard BiDi embedding rules rather than a literal mirror of the text. — https://flylib.com/books/en/3.147.1.90/1/ (Figure 7.5, visual inspection)
- .NET WinForms distinguishes "RTL reading order" (`Form.RightToLeft = true`, text/reading direction only) from full control-position "RTL layout" (`Form.RightToLeftLayout = true`, added in .NET Framework 2.0/Windows Forms 2.0): "the .NET Framework 1.1 does not move the System Menu, Close, Maximize, and Minimize buttons... [and] the locations of the controls on the form do not change." This distinction mirrors (pun intended) the native Win32 split between right-aligned text and full `WS_EX_LAYOUTRTL` window mirroring that Windows 2000 introduced at the OS level. — https://flylib.com/books/en/3.147.1.90/1/ (Figures 7.6–7.8 captions)

## Measurements

No independent pixel measurements of RTL-specific chrome (button sizes, title-bar height, bevel widths) could be sourced — every public image found was either a low-resolution book-scan photo or a non-native WinForms rendering, neither reliable enough for pixel-accurate metrics. Per the MSDN mirroring documentation, `WS_EX_LAYOUTRTL` is a coordinate/DC-level horizontal flip transform applied to the same chrome bitmaps used in LTR mode — it does not resize or re-space elements — so the working assumption for implementation is that **all standard Win2000 LTR system-metric values (caption height, button width/height, border widths) apply unchanged in RTL, only mirrored in position**. This is an inference from the mechanism, not a directly measured RTL screenshot.

| Title-bar button internal order, RTL | Close, Minimize, Restore (left→right) — full reversal of LTR order | medium (rendered WinForms sample only, not confirmed on native Win2000 chrome) | https://flylib.com/books/en/3.147.1.90/1/ |

## Colors

Not applicable — no evidence found of any Win2000/98 RTL-specific palette or theme changes; RTL/BiDi editions use the same system color scheme (`SysColor` values, 3-D face/highlight/shadow grays) as the LTR build. Only geometry/layout mirrors, not color.

## Behavior notes

- RTL is a per-window opt-in (`WS_EX_LAYOUTRTL`), not a single global screen transform — individual child windows can decline inheritance by clearing the style on `WM_CREATE`, which is why mixed LTR/RTL chrome (e.g. an LTR toolbar embedded in an RTL app) is possible and documented as a common source of bugs when developers use raw screen-to-client coordinate math instead of `MapWindowPoints`. — https://learn.microsoft.com/en-us/previous-versions/aa913269(v=msdn.10)
- Changing a running window's layout at runtime (e.g. a live language switch) requires re-toggling the `WS_EX_LAYOUTRTL` bit via `SetWindowLong` **and** calling `InvalidateRect`/`InvalidateRect(..., TRUE)` to force a full repaint in the new layout — the OS does not auto-repaint mirrored chrome on a style change. — https://learn.microsoft.com/en-us/previous-versions/aa913269(v=msdn.10)
- Message boxes require the explicit `MB_RTLREADING` option; simply running on an Arabic/Hebrew system does not auto-mirror a `MessageBox` call unless the app requests it, meaning many Win2000-era third-party apps likely shipped with unmirrored (LTR) dialogs even on RTL systems. — https://flylib.com/books/en/3.147.1.90/1/
- Directional icon assets used by shell/Explorer chrome (back/forward navigation glyphs, resize grips) are treated as data that must be separately authored/flipped for RTL builds — they are not automatically re-drawn correctly by the coordinate mirror alone if the bitmap itself contains baked-in direction. — https://www.chromium.org/developers/design-documents/ui-mirroring-infrastructure/
- BiDi text fields (address bars, path text boxes) keep embedded LTR runs (drive letters, file paths) rendered left-to-right even while the surrounding control/UI is right-aligned and RTL-flowing — standard Unicode BiDi embedding, visible in the Arabic Explorer address bar photo. — https://flylib.com/books/en/3.147.1.90/1/

## Open questions

- **The core open question — does the 3-D bevel light source mirror or stay physical? — could not be pixel-confirmed.** No sufficiently high-resolution, uncompressed color screenshot of native Win2000/98 Arabic or Hebrew button/title-bar chrome was found in reach (BetaArchive's wiki, which hosts a "Windows 2000 Build 2195 Pro - Hebrew" gallery of 24 screenshots and an "- Arabic" gallery of 5, is the single best-looking public source for this and is behind an active Cloudflare bot-detection challenge that this research avoided defeating). The best available evidence is *indirect*: MSDN's mirroring documentation states the RTL transform is a GDI device-context-level horizontal flip (`SetLayout(hdc, LAYOUT_RTL)`) applied to "bitmaps, icons... buttons" as part of the same window bitmap — which mechanically implies any baked-in 3-D bevel highlight/shadow would flip along with everything else (top-left highlight → visually top-right). But this is inferred from the documented mechanism, not directly observed at the pixel level on real Win2000 chrome, and it is plausible individual comctl32/user32 bevel-drawing routines special-cased the light direction to stay physically constant (the way logos/checkmarks are explicitly exempted from mirroring). This needs a real high-res screenshot or the (avoided, per clean-room rules) live system to settle definitively.
- Whether Explorer's tree/folder pane and content-list pane swap sides under RTL (tree normally left, content right in LTR) is genuinely ambiguous in the one photo obtained — the visible pane arrangement in the Arabic XP Explorer shot doesn't clearly resolve to a confirmed swap at this resolution; needs a sharper image.
- No Win2000-specific (as opposed to XP-era) native screenshots were found at all in publicly reachable, non-gated sources — every piece of photographic evidence here is Windows XP, and the WinForms mirroring illustration is a .NET 2.0 rendered sample, not real Win2000 shell chrome. The domain brief allows this substitution but it remains an evidence gap.
- Taskbar/Start button *exact* pixel position and size under RTL (does the Start button retain identical width/height, just anchored to the right edge, or does anything about its shape change) is unverified — only the qualitative "Start menu is on the right... taskbar extends from right to left" statement was sourced.
- Mixed LTR path text handling was only observed in one low-resolution photo; edge cases (e.g. a fully Arabic folder name mixed with an English drive letter, or UNC paths) are not covered by any source found.
- Control Panel / Regional Options screenshots showing the actual language-enablement UI (checkbox list including Arabic/Hebrew) were not located in accessible public sources during this pass.
